# 技术文章写作规范(见微)

> 本文是技术文章的通用规范。模型库专项细则见 `docs/development/model-library-writing-plan.md`; 两者冲突时以本文为准。
>
> 适用: 模型库对照稿(bi)/技术解析(analysis)/知识库一切技术文章。
>
> 新建知识库、面对陌生领域选择分类轴或设计整棵目录时, 先读 [`knowledge-base-design.md`](knowledge-base-design.md). 本文负责文件结构与文章写法, 该手册负责知识库类型、调研建树和拆分决策.

## 1. 总则

1. **读者锚点**: 训练, 推理与系统, 架构与数学, 评测与 Agent 四层都涉猎, 但都不深入。读者读过很多技术报告。不写谁都能答的入门内容, 不重讲教科书概念(RoPE, MHA, SFT, AdamW, next-token prediction)。
2. **说人话**: 去 AI 味。同型句式骨架(成串「不是 X, 而是 Y」)和「非常」类渲染词降密度。技术文按 `config/skills/shuorenhua/` 的 docs 场景 minimal 档过一遍, 保公式/数字/术语不漂移。
3. **直接陈述, 不写审计式元评论**: 不写「本篇只钉」「源文 §4.2」「先看配置」「把 37B 复核一遍」「证据状态」「流传的」「旧稿」这类交代改稿、迁移或审计过程的话。从模型本身说: 从架构上看, 从路由上看。作者亲自阅读时的困惑、惊讶和跨篇衔接不属于这类元评论, 按 §3.1 保留。
4. **Changelog 不进正文**: 变更记录(「● Updated...」「Fixed typo...」「### 2026 年 2 月 6 日」这类修订历史)是写给维护者看的, 不是给读者的。源文里的 Changelog 节整节删除, 页标记保留。
5. **数字必须有可追溯口径**: 原文数字给出表号、规模和实验条件; 自行计算的数字写出假设与计算过程; 无法复算的数字就不写。

## 2. 术语死命令

1. **专名留英文**: token, Scaling, Scaling Laws, decoder-only, MLA, MoE, MTP, CoT, GRPO, PPO, RoPE, GQA, YaRN, DPO, SFT, next-token prediction, RLHF。首次出现可写 **MTP** (一次再多预测一个 token), 之后只用英文缩写。
2. **禁用中文译名**: 令牌, 缩放律, 多令牌预测, 多头潜变量注意力, 混合专家, 思维链。
3. **保持中文**: 预训练, 微调, 强化学习, 编码器, 潜变量, 词表, 评测时。
4. **两条轴不许混**:
   - **缩放** 只指部署前把模型和数据做大(第一轴)。禁止用缩放说推理时多花算力。
   - **TestingTime** 是第二轴: 推理时多花的算力(test-time scaling / compute / reasoning)。中文禁止写「测时」「测试时」, 就写 TestingTime。
   - **评测时** 不是 TestingTime。评测时指跑榜, 保留中文。
5. 错例: 「测时算力成了第二轴: OpenAI o 系列缩放强化学习与测时推理」。对例: 「缩放指部署前投入更多算力. TestingTime 算力是第二轴: OpenAI o 系列把强化学习与 TestingTime 推理做大.」

## 3. 语言与标点

1. 中文正文全用**英文标点**: , . : ; ( ) " "。术语和专名按第 2 节。
   标点与空格整理只处理自然语言, 不改 Markdown、YAML、LaTeX、URL 或代码的语法符号. 图片标记必须保持 `![说明](路径)`, 不在 `!` 与 `[` 之间加空格; 数学命令、转义花括号、章节编号和 frontmatter 引号也保持原语义. 批量整理后既要检查源文件, 也要确认最终页面真的出现图片与公式, 不能只确认资源文件存在.
2. 中文引语用直角引号「」; 英文原文里的引号留在英文段。不要把整篇中文都换成直引号, 也不要用中文弯引号“”。
3. 加粗只给关键机制名和判断(负特征值, safe-completion, 路由器); 年份, 页码, 表号, 随手出现的百分数不加粗。机制解释不依赖比喻; 作者口吻里的短比喻按 §3.1 使用。
   - 加粗和直角引号不互斥, 可以同时出现: `**「推拉结合」**` 和 `「**自注意力只做一件事**」` 都可以, 按语义选择。
4. 长句优先拆短。能落到式子/表/图的判断, 必须指回去。
5. **重点必须能扫读出来**: 技术文章不能从头到尾保持同一视觉权重. 每个主要小节应挑出一到两个真正影响理解的机制判断、结论或边界, 用 `**...**` 加粗; 方法名、概念标签、需要辨析的短语和作者原话式命名可用直角引号 `「...」` 标出. 加粗不是给名词涂色, 也不是把整段变粗: 单个 `###` 通常不超过两处, 连续两段不要都以粗体句开头. 读者只扫标题和粗体时, 应能抓住文章的论证主线; 直角引号用于界定概念, 不能替代正常论述.

## 3.1 作者口吻与个人口癖

技术文章要准确, 也要让人认得出是谁写的. 下列说法是允许并鼓励保留的作者声音, 不要在「去 AI 味」时统一洗成无主语的公文。它们是语气样本, 不是每篇必须套用的模板。

1. **允许跨篇回指, 但必须让读者找得到**。同页可以写「前文已经讲过」「如前文所述」; 跨文章优先写成「上一篇 [文章名](链接) 讲到了 xxx, 那里只是简单说了一下, 这篇来深入讲解」。链接必须真实可达, 回指后用一两句复述本篇需要的前提, 不能逼读者跳走才能继续读。
2. **保留朴素的因果与收束句**。可以写「由于 xxx 的原因, 造成 xxx」「综上所述」。因果关系必须有公式、实验或前文论证支撑; 「综上所述」后面要真的收束前文, 不能接一段新的口号。同一句式连续出现时自然换写法, 不把口癖变成机器模板。
3. **允许第一人称留下真实的阅读阻力**。例如「我读了这么多论文, 第一次见到 xxx」「我很想把这个东西写清楚, 但是奈何我不懂」「我第一次看到的时候, 真的完全不懂」。下一段应继续说明究竟卡在什么定义、哪一步推导或哪组实验上, 并尽量把后来弄懂的部分写清楚。承认没懂可以标出知识边界, 不能代替查证和解释。
4. **允许无奈和暂时停步**。可以写「为之奈何」「好无奈」「前面的道路以后再来探索吧!」。使用这类结尾前, 先把尚未解决的问题、缺少的材料或推不下去的条件说具体; 不能用一句感叹遮住本来应该完成的推导。
5. **允许夸张比喻和突然拐弯的笑话**。例如「当我第一次见到 xxx 时, 我仿佛见到了奥特曼」, 也可以写英剧式的冷面笑话: 前半句一本正经, 最后一句轻轻错位。笑话服务于节奏、记忆点或作者反应, 不承担定义和论证; 正式公式、实验结论、安全边界与来源说明保持字面准确。不要照搬英剧台词。
6. **「奶龙笑.jpg」可以作为文字梗**。它表示一个读者能看懂的表情停顿, 不要求真的插图。若实际插入表情图, 仍要遵守图片来源、许可、alt 和图注要求。正文连续出现多个梗会冲淡技术主线, 留下最有效的一个即可。
7. **不设口癖配额**。有真实情绪时就写, 没有就直接讲技术。同一篇里反复出现「第一次」「奈何」「综上所述」会重新产生 AI 式模板感, 回读时删到只剩真正有作者反应的地方。

## 3.5 花园首页

首页是门脸，不是目录。机械罗列链接的写法一塌糊涂。

1. **散文定位**: 开头一段有味道的散文——这个花园回答什么问题、为什么存在、读完变成什么样。可以有一处符合 §3.1 的作者反应或短比喻, 随后落回具体研究问题。
2. **导航克制**: 不放裸链接清单，不放逐条罗列（文章列表由页面自动渲染，首页不需要复制一份）。链接按主线分组, 每组配成段的导读。
3. **给读法不给清单**: 内容多的园子给阅读路径（从哪进、按什么顺序、赶时间怎么读），让读者自己走进林子。
4. **门脸三禁**: 无元评论（改稿历史、迁移备注、工作流说明），无日期戳，无机器生成的 slug 列表。
5. **所有首页不少于 2000 汉字**: 花园首页, 章首页, 节首页一律适用. 篇幅来自真内容: 这一章各篇之间的关系和演进顺序, 共用的概念和记号在这里定义一次, 各方法的关键差别 (可以用对照表, 表后要有成段的解释), 按读者背景给的读法. 内容取自本章文章, 数字与正文一致. 不许凑字, 不许把每篇的摘要排成一列.
6. **禁止模板化导读**: 不写「本节回答的问题」「本章回答的问题」「这一篇回答什么」这类小节, 也不用「篇 | 回答的问题」这种表头. 文章直接进入材料和问题. 各篇的结构跟着内容走, 不要每篇都套同一副骨架.
7. **知识库目录树**: 第一层与第二层固定承担导航和参照系职责, 因而都必须是同名目录节点, 不能直接写成叶子 Markdown. 第一层使用 `{1-章}/{1-章}.md`, 第二层使用 `{1.1-路线}/{1.1-路线}.md`;只有到第三层 `{1.1.1-主题}.md` 才允许直接成为叶子. 第三层若还要容纳论文版本、案例或实现, 再升级为 `{1.1.1-主题}/{1.1.1-主题}.md`, 内部材料用 `01-`、`02-` 局部编号. `_garden.md` 是唯一可以直接位于知识库根目录的知识页面.

   **层级从花园内部开始计数, 不把知识库根目录和 `_garden.md` 算作一级.** 例如 `SparseAttention/2-动态路由/2.1-细粒度索引/2.1.1-DSA.md` 才是完整的“章 → 路线 → 主题”三级. `2-动态路由.md` 裸放在根目录、`2-动态路由/2.1-DSA.md` 裸放在章目录, 都属于结构错误. 第一、二层即使暂时只有一条下级路线, 仍必须保留可打开的同名首页;解决单子节点的方法是重新检查分类或补足真正的同级关系, 不是把二级节点降成裸叶子.

   中间层首页承担路线综述: 说明这条路线解决什么问题、方法之间按什么轴分化、先读哪篇以及共同使用哪些记号. 写到典型方法时, 用一两句点明关键改动并直接链接到该方法的详细解析页; 不在路线首页重复一遍详细页, 也不只列方法名和链接. 例如介绍动态索引路线时可以概括 DSA、HISA、MISA 的关系, 但推导、训练目标、内核和实验应进入各自叶子文章.

   | 节点类型 | 合法结构 | 说明 |
   |---|---|---|
   | 一级章 | `2-动态路由/2-动态路由.md` | 必须是同名目录与同名首页, 不允许根目录裸放 `2-动态路由.md`. |
   | 二级路线 | `2-动态路由/2.1-细粒度索引/2.1-细粒度索引.md` | 必须是同名目录与同名首页, 不允许章目录裸放 `2.1-细粒度索引.md`. |
   | 三级叶子 | `2-动态路由/2.1-细粒度索引/2.1.1-DSA.md` | 可以直接放在二级目录;需要下级材料时再使用同名目录. |
   | 花园首页 | `_garden.md` | 只放在花园根目录, 不再套 `_garden/`. |
   | 章或节首页 | `03-后训练/03-后训练.md` | 章或节必然承载下级内容, 所以属于非叶子节点; 花园根目录不计入知识层级. |

   判断时先看编号层级, 再看是否继续拆分. 一级和二级天然是父节点, 必须进入同名目录并提供同名首页;不得用“纯分组目录”规避首页. 三级通常是叶子, 只有继续容纳下级材料时才升级为同名目录. 纯资源目录不算知识节点, 例如 `images/`, `assets/` 和论文处理产生的中间目录.

   侧栏 (`PostTreeNav` 的 `buildTree`) 通过“Markdown 文件名与所在目录名相同”识别文章节点首页. 一级或二级缺少同名 Markdown 时, 侧栏只能显示无法打开的空节点;一级或二级直接写成 Markdown 时, 又无法承载下一层, 两种都属于结构错误. 第三级叶子后来新增下级材料时, 必须在同一次改动中创建同名目录、把原文移为同名首页并修正所有站内链接.

8. **编号与命名**: 同一父目录下的知识节点按显示顺序连续编号, 从 1 开始; 明确需要序章时可以从 0 开始. 删篇、挪篇或把叶子升级为父节点后都要重查同级编号, 不得出现 `01, 02, 04` 之类的断档. 同一层只用一种编号体系: 章节层使用 `01-`, `02-`; 章节内部可使用 `1.1-`, `1.2-`; 某一节下的论文或文章可重新使用 `01-`, `02-`. 同一目录不得混用 `01-` 与 `1.1-`, 有编号的同级知识节点中不得夹入无编号文章.

   目录名、文件名和标题各司其职. 目录与 Markdown 基名必须逐字一致, 包括编号、大小写和连字符; 文件系统名称不用全角冒号、顿号或空格. 有编号的知识页面, frontmatter `title` 必须以文件名中的同一编号开头, 例如 `1.2.3 · 正常中文标题` 或 `01 · 原始论文题名`;已有编号不重复添加, 变更编号时同步替换标题前缀. 标题主体保持原名, 不要求照抄文件名. `_garden.md` 不加编号, 无编号文章不从父目录推测编号, 日期文件名不作为知识编号. 内容重复的旧稿应删除, 所有站内链接改指保留稿; 不保留兼容副本、跳转壳文件或两套并行目录.

9. **结构变更验收**: 新建、移动、重编号或删除知识节点时, 必须同时检查父节点首页、侧栏层级、相对链接、图片路径和 frontmatter. 验收结果至少满足: 根目录除 `_garden.md` 外没有一级裸 Markdown;一级目录均有同名首页且至少包含一个二级路线;一级目录内没有二级裸 Markdown;二级目录均有同名首页且至少包含一个三级主题;只有第三层允许直接成为叶子. 换成路径写法就是 `1-主题/1-主题.md`、`1-主题/1.1-路线/1.1-路线.md`、`1-主题/1.1-路线/1.1.1-文章.md`. 同级编号连续且格式一致;目录名与文章首页基名一致;链接和图片路径可达. `TREE_L1_FILE`、`TREE_L2_FILE` 分别表示一级、二级节点裸放, `TREE_NO_INDEX` 表示同名首页缺失, `TREE_NO_ROUTE` 表示一级章没有二级路线, `TREE_NO_LEAF` 表示二级路线没有三级主题;单库必须由 `node scripts/content-check.mjs tree --garden=<知识库 slug> --list` 验收为零, 全部迁移完成后再运行不带 `--garden` 的全库检查.
10. **顶级目录使用正式英文名**: 技术知识库的顶级目录采用区分大小写的 `PascalCase` 正式英文名称, 不使用全小写 slug, 也不单独使用领域缩写, 例如 `OnPolicyDistillation`、`RecursiveSelfImprovement`、`LongHorizonTask`. 品牌、项目和课程沿用官方大小写, 例如 `DeepSeek`、`OLMo`、`StanfordCS336`;行业中已经作为基本词汇使用的 `LLM` 可以保留, 例如 `LLMInfrastructure`. 花园 `title` 和正文 H1 面向读者写清英文全称与中文含义. 标题用于解释这座库是什么, 不把宣传语、版本号或文章数量塞进名称.

### 3.5.1 页面职责与拆分时机

文件树表达知识关系, 正文结构表达论证关系. 两者必须一起设计, 不能先把文件随意摊平, 再靠首页补链接;也不能为追求目录层数把一篇完整论证机械切成几份.

1. **花园首页给全局坐标**: 说明领域为什么形成, 几条主线怎样相连, 读者可以从哪里进入. 可以使用路线图或家族对照表, 随后必须有成段解释. 首页不承担某个算法的完整推导.
2. **章首页建立共同问题**: 定义本章共享的对象、反馈来源、参照方法与比较口径. 例如偏好优化章先区分比较数据、reward model、reference 与在线采样, 再分 RLHF 和直接偏好优化. 章首页不把每个叶子算法各摘要一遍.
3. **路线首页建立家族参照系**: 三个以上叶子方法共享一套起点、记号或失效模式, 且这些共同内容足以写成不少于 2000 汉字的独立文章时, 增加真实的中间节点. 路线首页先把 baseline 推到可比较的位置, 再说明各叶子究竟改了哪一个量. 例如 `偏好优化 → 直接偏好优化 → DPO / IPO / ORPO / SimPO / KTO`.
4. **算法叶子完成一条闭合论证**: 写清问题在什么约束下出现, 朴素 baseline 怎样运行、解决了什么又留下什么, 再解释后续方法分别改变哪个变量、为什么可能有效、证据有多强以及新增了什么代价. 材料适合从反常实验、版本变化或旧路线复活进入时, 就从那里进入. §3.5.2 给出完整的思考框架;它约束论证是否闭合, 不规定小标题和段落顺序.
5. **比较页只做真正的横向比较**: 先固定基础模型、数据、采样预算、奖励、reference 和指标口径, 再比较算法. 如果一页主要在讲某个方法自己的推导, 就归入该方法叶子, 不因为标题里出现“对比”便另建比较节点.
6. **中间层的内容条件**: 第二层目录与首页是固定结构, 但不能因此写成几行链接的壳页. 暂时只有一个三级叶子时, 二级首页仍要讲清共同问题、记号、边界和它与相邻路线的区别;若这些内容写不出来, 应重画分类轴或把相关方法补进来. 方法很多但彼此没有共同 baseline 时, 应分到不同路线, 不能只因为缩写相近塞进同一目录.
7. **正文去重按职责处理**: 共同定义、统一记号和家族比较留在上层首页;完整公式、手算、伪代码、实验数字与单篇论文边界进入叶子. 上层提到典型方法时用一两句点出改动并链接, 叶子不再重写整章导论. 迁移内容后逐段检查, 不用删除整篇或回滚整个版本代替去重.
8. **导航来自结构, 不是正文模板**: 侧栏由目录树生成, 正文无需重复一份裸目录. 页面开头可以给前置链接或阅读顺序, 但不能让每篇都出现完全相同的“一句话、动机、方法、实验、参考”七段标题. 统一的是读者需要获得的信息, 不是标题措辞和段落数量.

### 3.5.2 算法发展因果链

算法史的主线是问题和约束怎样推动方法演进. 单按年份排列论文, 这条线很容易被论文名淹没. 一条技术路线真正需要讲清的是: **问题怎样在一组具体约束下产生, 朴素解法把问题推进到哪里, 哪些故障仍然存在, 后续算法分别改了什么, 这些改动为何有效, 又把代价转移到了哪里.** 读完以后, 读者应当能够面对一篇新论文, 自己判断它修改了数据、状态、目标、估计器、模型结构还是系统实现, 以及它解决的故障是不是当前场景的主要瓶颈.

写作时在脑中检查下面这条因果链:

1. **问题与外部条件**: 目标是什么, 当时受哪些硬件、数据、规模、接口和训练阶段约束, 原方法又默认了哪些假设. 同一个算法在不同约束下可能得到相反评价, 所以不能先写“谁更好”再补条件.
2. **可运行的朴素 baseline**: 说明输入、输出、中间状态、数据来源和目标函数;给出必要的复杂度或小规模手算;同时交代它在哪些条件下已经够用. 后续方法必须能指回这个参照点.
3. **沿因果链拆故障**: 把“效果差”拆成目标偏差、估计方差、状态覆盖、优化不稳、系统吞吐、模型容量、数据质量或评测口径等可区分原因. 不同故障需要不同修法, 不能用一个算法名覆盖整条链.
4. **算法究竟改了哪个变量**: 固定其余条件, 说明方法改变了轨迹来源、反馈粒度、散度、采样器、状态表示、网络结构、更新规则还是硬件映射. 同一家族的方法放在共同坐标中比较, 不逐篇复述摘要.
5. **为什么有效以及证据有多强**: 严格区分四种证据. **理论证明**给出假设下的收敛、无偏性、方差或复杂度结论;**机制推导**解释梯度、概率质量或状态怎样变化;**受控实验**在固定底座、数据、预算和解码后验证因果变量;**大规模实践规律**来自多个规模、任务或系统的重复观察. 机制推导不能直接冒充 benchmark 结论, 经验规律也不能写成无条件定理.
6. **新问题与代价转移**: 每个改进都要追踪新增代价. 稀疏计算可能引入索引器和不规则 kernel;critic 提供状态条件化估计, 同时引入价值偏差和额外训练;回放提高利用率, 同时增加策略陈旧. 算法解决了多少、代价转移到哪里, 决定它是否真的适合当前场景.
7. **后续分叉与负结果**: 说明后续方法分别修哪一个遗留故障, 包括理论漂亮但假设不成立、只在小规模有效、benchmark 上有效却无法部署的路线. 失败方法可以解释设计空间为何收敛到今天的位置, 不应从技术史中消失.
8. **旧路线为什么复活**: 检查硬件、模型规模、数据、上下文长度、训练阶段、系统组件和评价目标是否发生变化. 过去的主要缺陷可能被新 kernel、可靠验证器或更大规模摊薄, 也可能只是降为次要矛盾. 写清变化的外部条件, 避免用“风水轮流转”代替原因.
9. **算法贡献与系统增益分开**: 横向比较尽量固定底座、数据、训练 token、采样预算、推理预算、奖励、解码方式和硬件实现. 若收益主要来自更强基础模型、更长输出或新 kernel, 就按实际来源说明, 不全部记到算法名下.
10. **形成选择能力**: 文章结尾可以总结, 但总结应收敛成条件判断. 读者需要能够回答“长度扩大十倍时哪个假设先坏”“教师只能返回文本时哪些目标失效”“硬件不支持不规则稀疏时 FLOPs 降低是否有意义”这类问题, 而不只是背出论文结论.

**这十项是作者脑中的检查框架, 不是正文模板.** 禁止把每篇文章机械写成十个同名小节, 也禁止为了覆盖检查项补空泛段落. 具体文章应从材料最有力量的位置进入:有的从朴素方法的失败开始, 有的从一条反常实验曲线开始, 有的从硬件条件变化带来的旧算法复活开始. 标题、顺序和篇幅都跟着论证走, 最终让上述因果链在全文中闭合即可.

### 3.5.3 目录编号

编号必须让读者直接看出页面位于知识树的哪一层, 做法与 `content/llm-guide` 一致.

1. 第一层章使用 `1-基础`、`2-检索`；第二层使用 `1.1-问题定义`、`1.2-经典方法`；第三层最多写到 `1.1.1-具体主题`、`1.2.6-具体主题`.
2. 禁止出现 `1.1.1.1` 这类四段层级编号. 当 `1.1.1` 还需要容纳多篇论文、版本或案例时, 把它建成同名目录, 内部文章重新使用局部序号 `01-`、`02-`、`03-`;局部序号不继续表达知识层级.
3. 同一层级不得机械地全部重启为 `01-`、`02-`. `01-` 只用于第三层节点内部的材料顺序, 不能代替 `1.1` 或 `1.1.1`.
4. 编号深度直接约束文件形态: 第一层、第二层必须使用同名目录与同名首页;第三层才允许直接作为叶子 Markdown. 第三层继续拆分时使用同名目录, 内部材料重新以 `01-`、`02-` 编号.
5. 新建或重排知识库时, 先用无编号的主题树检查分类轴, 再赋编号. 如果必须靠编号才能看出若干页面为何放在一起, 说明主题关系还没有拆清楚.
6. 目录编号同时写入 frontmatter `title`, 让桌面与手机上的标题直接显示知识树位置. 用 `node scripts/content-title-numbering.mjs` 检查;修正用 `--write`, 只改标题编号, 不改正文、摘要、目录或 slug. `node scripts/content-check.mjs frontmatter` 同时检查标题编号.

## 3.6 技术文章硬规范

1. **机制解释禁止依赖比喻/类比/拟人化**. 定义、公式、实验结论直接陈述, 用可复算的小例子降低理解门槛。§3.1 的短比喻可以表达作者第一次见到材料时的反应, 但比喻之后必须回到真实对象, 不能把「像什么」当成「它怎样工作」。
2. **默认不写 `## 太长不看版`**. 只有正文超过约 10000 汉字, 且内容确实能收成几条确定结论和数字时才加. 推导型、综述型、多机制并列和讲过程的文章不写. 需要时只写一段三到五句, 不复述目录, 不列清单, 小标题不叫「先给结论」.
3. 符号第一次出现就地解释 (包括输入从哪来), 不甩符号表, 不跳步. 术语前后一致, 改名必须交代「X(即前文的 Y)」.
4. 每个机制写清四件事: 谁算, 谁和谁计算, 缓存/状态怎么变, 丢了什么.
5. 正文中的符号、变量、下标和短式子用 `$...$` 包裹 (写 `$\theta_k$`、`$d_k=3$`), 不裸写 LaTeX. 推导、编号或较长式子用 `$$` 独占一行. 文字讲到哪一步, 公式就跟到哪一步; 每个式子都要解释它推进了哪一步.
6. 代码块只放需等宽的纯 ASCII 图 (掩码/层排布/路线图), 禁止在代码块里写伪公式.
7. **少用指代**: 「这套」「那个」「它」「同样的」必须落成具体名词; 前文没讲清的先补定义再引用.
8. 变量注释用 `\underbrace` 挂在单个变量下方 (一个变量一条, 不许多变量共用一个大括号).
9. **篇幅**: 每一篇正文不少于 5000 汉字, **通常控制在 8000–12000 汉字**. 超过 12000 汉字时, 必须存在无法自然拆开的连续推导、版本演进或实验论证;超过 15000 汉字时, 原则上拆成真实叶子或压缩. 篇幅来自把机制、推导、实验、前后版本和边界讲透, 不来自重复前文、套话、空泛总结、通用工程检查表或换说法再讲一遍. 材料本身单薄时, 可以补相关技术的来龙去脉和对照, 每一处都要有出处;补完仍不足 5000 时记录材料边界, 不为达标制造内容.
   - 适用范围: 正文文章. 花园首页 `_garden.md`, 章首页, 节首页按 §3.5 第 5 条, 不少于 2000 汉字.
   - **少分节, 少分点**: 一篇正文的 `##` 一般 3 到 5 个, 最多 6 个 (参考文献不计). 每个 `##` 通常放 2 到 4 个 `###`, 全篇 `###` 通常控制在 8 到 16 个; 禁止把几十个平级小节从 `5.1` 一路编号到 `5.28`, 也禁止改用 `**5.28. ...**`、列表项或同段粗体继续模拟第四级标题. 相邻小节若共享同一个问题、推导或实验, 合并成连续段落、表格或一次完整走查. 撑不起两个子节的 `##` 并进相邻大节. 列表最多 5 项, 超过的改写成段落或表; 不要用列表代替论述, 能写成连贯段落的就写段落.
   - **一个标题下不许只有一段话**: 任何 `##`/`###` 标题下 (到下一个标题前) 至少两段成文的内容; 只有一张表, 一个式子或一个列表也不行, 必须配解释段. 内容只够一段的, 并进相邻小节, 删掉这个标题, 不要为了撑出第二段去凑字. 合并后重排节号, 文中的「§x.y」「第 x.y 节」引用同步改.
   - 例外: 一个主题确实讲透了还不到 5000, 再写只能加空洞内容时, 就不到 5000. 这个例外要慎之又慎: 先查机制, 推导, 实验, 前后版本, 边界条件, 工程细节是不是都讲到了; 同主题的短篇能合并的先合并. 都做了还不够, 才停.
10. **不能有 AI 味**: 写完按 `config/skills/shuorenhua/` 或 `.cursor/skills/humanizer-zh/` 回读一遍. 重点查: 开头和结尾的套话, 口号式总结, 成串的「不是 X, 而是 Y」, 「非常 / 深刻 / 至关重要 / 本质上」一类渲染词扎堆, 三连排比, 每段都以加粗金句收尾, 「值得注意的是 / 需要指出的是」一类空转连接词, 以及审计式元评论 (见 §7). 同一种句式骨架在一节里出现三次以上就改写.

### 3.6.1 数学记号与张量方向

同一篇文章只使用一套向量方向和索引语义. 原论文采用另一套约定时, 可以在第一个式子前声明转置关系, 然后把整套公式一次性转换过来. 禁止逐式猜测行列方向.

1. **样本与分布分开**: 类别数为 $K$ 时, 离散状态的 one-hot 样本写为行向量 $x_t\in\{0,1\}^{1\times K}$, 类别概率写为行向量 $p_t\in\Delta^{K-1}$. $x_t$ 是一次实现, $p_t$ 是分布; 不用同一个符号在两种含义之间切换.
2. **离散转移矩阵按行表示出发类别**: $Q_t\in[0,1]^{K\times K}$ 满足

   $$
   Q_t[i,j]=q(x_t=j\mid x_{t-1}=i),\qquad Q_t\mathbf 1=\mathbf 1.
   $$

   因此 $Q_t$ 行随机, 每行和为 $1$. 一步前向为 $x_{t-1}Q_t$ 或 $p_{t-1}Q_t$.
3. **累积转移按时间顺序右乘**: 定义 $\bar Q_t=Q_1Q_2\cdots Q_t$, 则 $q(x_t\mid x_0)$ 的类别概率为 $x_0\bar Q_t$. 必须在首次出现时展开一次 $\bar Q_t$ 的乘法顺序.
4. **后验的前驱项使用转置**: 在上述行向量约定下, $x_tQ_t^\top$ 枚举每个候选前驱状态转移到当前 $x_t$ 的概率. 离散扩散的一步后验可写为

   $$
   q(x_{t-1}\mid x_t,x_0)
   =\operatorname{Cat}\!\left(
   x_{t-1};
   \frac{(x_tQ_t^\top)\odot(x_0\bar Q_{t-1})}
   {x_0\bar Q_t x_t^\top}
   \right).
   $$

   分母 $x_0\bar Q_t x_t^\top$ 是标量, 分子是对 $x_{t-1}$ 各类别的未归一化概率.
5. **离散时间矩阵与连续时间生成元分开**: $Q_t$ 是行和为 $1$ 的随机矩阵. 连续时间 Markov 链的生成元记为 $R_t$, 满足 $R_t[i,j]\ge 0\ (i\ne j)$ 和 $R_t\mathbf 1=0$, 前向方程为

   $$
   \frac{\mathrm d p_t}{\mathrm d t}=p_tR_t.
   $$

   当 $p_t[i]>0$ 时, 反向过程的非对角跳转率为 $R_t^{\leftarrow}[i,j]=R_t[j,i]p_t[j]/p_t[i]$, 对角元由每行和为零确定.
6. **避免符号冲突**: 同篇文章同时讨论扩散转移和 attention Query 时, $Q_t$ 保留给转移矩阵, Query 改用 $H W_Q$ 或带明确上标的符号. 连续嵌入扩散的高斯状态与离散 token 状态也要分开命名.
7. **代码 shape 不改变数学约定**: 实现中可以增加 batch、sequence 和 head 轴, 但要在 `matmul`、`einsum` 或 gather 旁写清各轴含义. 代码至少断言输入 shape、矩阵非负性和归一化方向.
8. **用小例子检查方向**: 选两类或三类手算一步转移、累积转移和后验, 检查概率非负且和为 $1$. 连续时间情形还要检查 $\exp(hR_t)$ 在误差内为行随机矩阵. 这类检查应进入正文手算或配套代码, 不只写在作者的工作笔记里.

## 3.7 作者的拆解方式与表达习惯

下列方法用于选择最适合当前材料的讲法, 不对小标题、段落顺序和篇幅做固定。

### 3.7.1 拆解方式

1. **先讲它要解决的困难, 再讲它是什么.** 2.1.2 开头先写「训练深层网络非常依赖初始化, 学习率和梯度裁剪」, 再引出归一化. 不从定义起笔.
2. **先摆粗略说法, 再给更严格的理解.** 「最常见的粗略说法是: 归一化层可以减少内部协变量偏移. 这种说法有启发性, 但不够准确. 更严格的理解是……」. 指出粗略说法哪里不准, 不是直接否定它.
3. **用真实问题组织论证**. 问题可以自然出现在开头或小标题中, 但不固定列「本文回答的问题」清单.
4. **公式一层层往下展开到能算的程度.** 矩阵式 → 单个 token 的行向量 → 按分量求和. 每展开一层, 紧跟一句这一层回答了什么: 「这一步看起来只是把向量写长, 但它其实回答了一个很实际的问题: 后面所有点积, softmax 和加权求和, 最终都是在这些坐标分量上发生的.」
5. **每个量出现后说它回答什么问题.** 「$\mu_L$ 回答的问题不是这一批样本平均怎样, 而是这一个 token 自己当前整体偏到哪里去了.」
6. **小维度手算, 一步不省.** 2.2.1 用 `[大模型, 太, 牛逼, 了]`, $d_k=3$, 把点积, 缩放, softmax 的分子分母, 逐维加权全部写出来, 最后放回矩阵视角: 「矩阵公式没有比标量公式多做别的事, 它只是把每个 token 都做一遍同样的计算并行化了.」 反向传播用「步骤 | 计算 | 结果」的走查表.
7. **同一对象的几个视角放进一张表**: 视角, 一句话版本, 回答的问题. 并写明哪个视角只是近似, 它在哪里不准 (「软检索视角是近似: 真实检索是 hard top-k, 注意力是对所有 Value 的 soft 混合」).
8. **对照着讲两个相近的方法**, 落到同一个可比的维度上. BatchNorm 和 LayerNorm 比的是统计轴; Post-Norm 和 Pre-Norm 并排写两个式子: 「这两个公式看起来只是顺序交换, 但训练行为差异很大.」
9. **讲「为什么不适合」时分条给原因**, 写在段内: 「原因主要有三个. 第一……第二……第三……」.
10. **把适用条件写进结论.** 说明结论依赖的对象、尺度、假设或实现条件. 不在有力度的判断后追加「这是主观看法」「不是公认标准」「也不意味着……」之类防御性声明.
11. **每张图紧跟图注, 图注后再写「图 N 解析」.** 图片下一行必须是图注 `> 图 N: <这张图画的是什么>` (一句完整话, 写清对象, 横纵轴或模块, 出处如「原文 Figure 3」); 连续几张子图共用一个图注, 写在最后一张下面. 图注之后才是「图 N 解析」, 2–4 条: 节点和边各是什么, shape 是什么, 图里没画什么, 不能据此推出什么. 只给实际存在的图写; 图没有就不写解析. bi 稿里原文有英文题注的保留原文题注 (题注不译), 原文没有题注的图补一行中文图注. 图片统一放在文章所在目录的 `images/` 下, 不建 `<文章名>-images` 这类平级目录. 检查: `python scripts/caption-check.py <目录>`.

   配图选题、制作与验收按 §3.8 执行.
12. **落到工程检查项.** 归一化层最后按训练, 量化, 长上下文三个场景列「该监控什么」. 工程影响常按训练, 推理, 量化三段分开讲.
13. **代码对应公式.** docstring 写「对应公式: ……」, 注释写 shape, 用 assert 验维度, 手算梯度和 autograd 对照打印.
14. **出处跟在第一次提到的地方**: [Ba, Kiros, & Hinton (2016)](https://arxiv.org/abs/1607.06450) 提出的 Layer Normalization. 历史只给年份, 人物和一句后果 (Minsky 和 Papert 1969 年证明单个感知机只能解线性可分问题).
15. **讲完好处, 紧跟代价.** 「但代价是位置上限被固化在参数表中」「但 ReLU 也有明确代价:」. 对比表的最后一列通常是「代价」或「想解决的问题」.
16. **演进史按「每一步补上一步的缺口」排**, 最后把几条路线的分歧收成一个轴: 「这几条路线的分歧, 不在有没有位置信息, 而在位置信息应该加在哪一层」.
17. **展开后交换求和顺序, 让原式里看不出的结构露出来.** MHA 式 (12) 把检索权重 $\alpha$ 和 $W_V$ 拆开; MLA 把分数写成系数与位置无关的双线性型, 由此得到矩阵吸收.
18. **一族方法放到同一条参数轴上, 两端退化成已知方法.** GQA 的组数 $G=H$ 是 MHA, $G=1$ 是 MQA; Block AttnRes 的 $N=L$ 是 Full AttnRes, $N=1$ 退回标准残差.
19. **先立参照系, 后面只写相对它改了什么, 没改什么**: 「MQA 不改变式 (8) 的形式; 压缩只发生在 cache 里的 $k_s, v_s$」.
20. **同名方法按「作用在哪一截张量上」区分**: 注意力子层从输入到残差加法有六处可以加门, 列一张表写清每个方法加在哪一处.
21. **推理按 Prefill 和 Decode 分开算**, 计算量和访存各算一遍; 「存下来的」和「临时算的」分开: 历史 Q 不存也不读, 是计算, 不是缓存.
22. **数字标口径**: 来自哪张表, 哪个规模, 训了多少 token. 正面陈述 (「74.64 是 Table 1 的 Hellaswag 一列」), 不写成「核对要点: 不是 MMLU」.
23. **消融逐条写「换掉了什么, 数值变成多少, 为什么」**: 「softmax 换成 sigmoid, 1.741, 缺了竞争归一化」.
24. **失效模式按因果链展开**: 写清触发条件、直接后果、可观测信号和修复手段; 内容足够时再单独成节.

### 3.7.2 句子习惯

1. 术语第一次出现就地解释, 括注英文: 「logits 指模块在 softmax 或离散决策前输出的原始分数」「reduce 指沿某个维度把很多数聚合成少量统计量」.
2. 一句话记忆点, 加粗单独成段: 「**自注意力只做一件事: 在 token 之间搬运信息——QK 决定从哪搬, OV 决定搬什么, 写去哪.**」 后面紧跟一段解释这句话为什么比常见说法更接近本质.
3. 核心判断加粗: 「**归一化不是通用的, 而是强依赖数据结构和推理模式.**」 一节最多一两处.
4. 需要改写前句时可用「也就是说」或「换句话说」, 但不得连续出现. 「不是 X, 而是 Y」只在确实需要纠正常见误解时使用, 不当通用连接词.
5. 例子可以口语化 (「牛逼」「拍桌子」「这个方法不是白送的」), 但数字必须能复算. 口语只用于增加节奏和表达判断, 不代替机制解释.
6. 公式前的引导写动作: 「代入式 (7)–(8) 可得:」「交换求和顺序:」「同理:」, 或「X 给出的形式是:」. 公式后马上解释符号, 再用「式 (N) 说明……」接一句它的作用.
7. 手算前先声明假设和省略了什么 (「省略 RoPE 与 $\sqrt{d_h}$ 缩放」「仅示意, 非训练所得」), 再分步, 每步标对应的式号.
8. 小标题可以是问句, 正文第一个词直接回答: 「约束和为 1 会不会降低表达力——不会, 前提是……」.
9. 用「只」「仅」划清改动范围: 「GQA 的改动仅在 cache 的 KV 组数 $G$」.
10. 代码注释写 shape 和共享关系; 代码后一段写「这段代码说明两件事. 第一……第二……」或逐项列「`inv_freq` 对应式 (3) 的频率谱」.

- 自己写的抽象式后面声明「这不是论文原式」. 有原式用原式; 需要抽象时直接写, 不加声明.

## 3.8 图文并茂与科学配图

**图片是技术论证的一部分.** 核心机制、状态变化、方法对比和公式推导应结合图像讲解. 正文已经解释过的知识点, 仍可整理为机制图、比较图或复习卡片; 图片承担空间对应、并列比较和回顾的作用. 按理解需要选图, 不按篇幅机械分配张数.

1. **画到机制内部**: 展开输入、关键操作、中间状态和输出. 注意力图应呈现 token 或 block、矩阵、索引与共享关系; 蒸馏图应呈现轨迹来源、评分条件、概率分布与更新对象; 长程任务图应呈现动作、环境反馈、时间位置和信用分配. 只有方法名、几个方框和箭头时, 继续补足能解释方法的局部结构.
2. **先读论文原图**: 论文已经提供架构、流程、注意力模式或实验图时, 打开对应 PDF 或高清原图实际查看, 同时阅读图注、相关公式和正文. 记录论文、版本、图号与来源链接. 可以保留清晰的原图, 也可以据此重画中文教学图, 或制作总览加局部展开. 原图决定机制, 视觉参考提供布局、字体和配色. 原图缺失时继续寻找官方论文、项目文档或源码中的结构依据.
3. **机制教学图实际加入生图**: 使用 Image 2.5 生成候选, 结合科学配图 skill 与 [AstraDraw](https://github.com/IamJerryXu/AstraDraw) 的结构分析. 流程为「读源文与原图 → 确定要解释的变化 → 列出对象、运算与连接 → 输入已查看的参考图生成 → 回读科学内容 → 局部修正 → 正文尺寸验收」. 参考图通过生图接口实际传入, 提示词说明借用哪些结构与视觉元素. 接口无法指定或确认模型版本时如实记录, 不把其他模型标成 Image 2.5. 生成的 PNG 可以直接用于文章;需要可编辑交付时, 再用 PPT 原生对象重建模块、文字与连接, 保存源文件和 PNG.
4. **实测结果由数据绘制**: 实验曲线、柱状图、散点图、热力图、消融与多面板结果图参考 [figures4papers](https://github.com/ChenLiu-1996/figures4papers), 用确定性代码生成 SVG 与 PNG. 保存数据、单位、坐标范围、误差带和比较条件, 正文展示 PNG. SVG 可作为绘图源文件保留. 教学用的小概率分布、优势条形图或矩阵可以经过生图, 但数值必须先手算或用代码复算, 图内标明「教学示例」. 实测数据、示意数值与概念模式分别标识.
5. **技术文章的视觉风格**: 白底或浅底, 清楚的文字和数学符号, 克制的配色, 明确的线条与分组. 用 token 条带、矩阵、分布、时间轴、局部展开和小规模手算增加信息量. 颜色编码保持一致, 同时用标签、线型或形状辅助区分. 不用卡通人物、装饰性机器人、发光背景或大面积空卡片填充版面. 高密度图可以拆为总览和细节图, 保证文章实际显示宽度下仍能读到关键标签.
6. **逐项复核公式与连接**: 检查条件变量、上下标、shape、归一化方向、运算顺序、冻结与更新对象、时间边界、共享参数和 gate. 例如 attention 的 V 进入概率加权步骤, OPD 的师生概率条件于同一学生前缀, GAE 的残差与优势按时间递推. 箭头端点对应实际对象, 评分、数据、梯度与时间反馈使用可区分的连接. 图内所有手算数值与正文一致, 输出图需要重新查看后才可嵌入.
7. **图与正文一起读**: 图放在读者需要理解该机制的位置, 紧跟图注与必要解析. 图注说明对象、轴或颜色与来源;论文、版本、图号和链接放在图外的正文图注或来源记录中, 图面不出现「依据原文 Figure N 重绘」这类制作说明. 解析引导读者跟随一次计算、一次状态变化或一组比较, 避免再抄一遍图中标签. 首页适合路线图与家族比较, 叶子文章适合机制展开与推导手算, 内容自然选择表达方式.
8. **辅助素材与源文件**: [ml-paper-icons](https://github.com/Mizar77/ml-paper-icons) 用于识别模型、存储和工具等对象, 使用前核对素材许可. 科研 Poster 使用 [pptx-posters](https://github.com/K-Dense-AI/scientific-agent-skills/tree/main/skills/pptx-posters) 与 `Presentations` 的尺寸、打印和版面工作流. 配图保留来源、提示词、必要的数据或编辑源文件; 正文使用可访问的本地图片路径.
9. **保留有用的图**: 已有卡片或流程摘要能够帮助理解、对比或复习时保留. 对关系错误、文字错误或难以阅读的图, 优先修正或重制, 再决定是否删除. 不能用批量删除代替逐张判断. 图片替换后同步图注、解析和引用, 检查分辨率、截断、遮挡、路径与文件格式.
10. **概念与标签有上下文**: 图内概念必须已经在此前正文或图内得到解释, 不能突然插入未定义的方法名、变量或模块. 领域内常用且无需特意解释的术语可以直接使用, 其余概念用简短定义说明作用. 标签按第 2 节选择中文或保留专名, 不写无意义的「英文 (中文翻译)」双语标签;确需对照术语时放在正文定义处, 不挤占图面空间.
11. **框线与箭头完整**: 矩形模块保持规整, 避免无必要的扭曲、重叠和遮挡;只有表达嵌套、共享或叠层等实际关系时才采用相应布局, 并使边界和标签清楚可见. 连线必须完整连接明确的起点与终点, 禁止意外断线、悬空箭头和看不出来源或去处的连接. 有含义的虚线须连续可追踪, 并在图例中说明;分面之间的连接使用对应标记说明两端关系.
12. **架构流向与变量生命周期**: 网络结构复杂、文字难以表达连接关系, 或连续公式难以看出计算过程时, 配图展开实际数据流与计算依赖. 架构图明确输入经过哪些模块、产生哪些中间量及输出. SparseAttention 等大量复用状态的机制尤其要标明变量在哪一层、哪一步或哪个时间区间产生, 哪一步计算完成或写入缓存, 后续被哪些操作使用, 复用跨越哪些 head、layer、block 或 step, 何时更新或失效. 用时间轴、层索引、缓存边界和分支连接表达这些关系, 区分重新计算与读取复用, 不能用一根含糊的「共享」箭头概括. 例如索引分数、选出的 token 索引与缓存中的 K、V 是不同对象, 应分别连到后续实际使用它们的操作;跨层或跨步复用时, 两端标明对应的层号或步号. 回读图时逐个追踪关键变量: 从哪里算出, 何时可用, 存在哪里, 后续哪些操作读取, 哪个条件下需要重算.

## 7. 技术解析(analysis)规范

1. 不是第二遍翻译, 不是辞藻堆砌。写这篇真正用到的技术的前世今生: 它是什么, 为什么这样设计, 怎么做, 代价, 在这篇怎么用, 与其他技术怎么拼, 效果, 同队前后版本改了什么。这些是思考线索, **禁止当小节标题抄**。
2. llm-guide 已有推导就链接(先确认文件存在, 相对路径 ../../../../llm-guide/..., 文件名里的中文冒号不改), 不重推 MLA, RoPE, GRPO, PPO。
3. 小节编号: 篇名 `#` 不编号, 大段 `## 1.`, 机制 `### 1.1.`, 需要才用 `#### 1.1.1.`。每个有内容的 ## 至少两段中文。禁止通篇同级标题一路排, 也禁止小标题一串每节两三行。
4. 篇幅按 §3.6.9 执行. 短公告或模型卡材料不足时, 补这篇用到的技术演进、同队前后版本和相关论文机制, 每处给出来源; 仍然禁止编造架构或凑字.
5. 长度跟着机制走: 论文规定了几件就讲完几件, 讲完了短就保持短。公式按项写开, 消融写清关掉的是哪个量, 配比/日程/损失写到能复述。
6. 禁用词按第 4 节; 不写审计式元评论。报告没有给出的数字不得猜测, 也不要把「报告没写」「无法确认所以不写」之类的审稿说明塞进正文; 缺失项若会影响结论, 直接陈述可核查的适用条件或局限, 源文缺页缺图且无法补救时记入 `docs/development/paper-issues.md` 后跳过。
